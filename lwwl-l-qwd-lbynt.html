    9. الوصول إلى قواعد البيانات

    9.1. الموصل ADO.NET

    لنعد إلى بنية الطبقات المستخدمة في مناسبات عديدة

    في الأمثلة التي تمت دراستها، استخدمت الطبقة [dao] حتى الآن نوعين من مصادر البيانات:

    • البيانات المضمنة في الكود
    • البيانات الواردة من ملفات نصية

    ندرس في هذا الفصل الحالة التي تأتي فيها البيانات من قاعدة بيانات. تتطور بنية الطبقات الثلاث عندئذٍ إلى بنية متعددة الطبقات. وهناك أنواع مختلفة منها. سندرس المفاهيم الأساسية باستخدام ما يلي:

    في المخطط أعلاه، تتواصل الطبقة [dao] [1] مع SGBD [3] من خلالمكتبة فئات خاصة بـ SGBD المستخدمة والمرفقة معه. تنفذ هذه الطبقة وظائف قياسية مجمعة تحت مصطلح ADO (Active X Data Objects). يُطلق على هذه الطبقة اسم مزود (مزود الوصول إلى قاعدة البيانات هنا) أو موصل. تتوفر الآن معظم ملفات SGBD بموصل ADO.NET، وهو ما لم يكن الحال عليه في بدايات منصة .NET. لا توفر موصلات .NET واجهة قياسية لطبقة [dao]، لذا تحتوي هذه الطبقة في كودها على أسماء فئات الموصل. إذا تم تغيير SGBD، يتم تغيير الموصل والفئات، ومن ثم يجب تغيير الطبقة [dao]. هذه بنية فعالة لأنها مرنة، حيث إن الموصل .NET قد كُتبت من أجل SGBD معين، فهي تعرف كيف تستخدمه على النحو الأمثل، وهي صلبة أيضًا لأن تغيير SGBD يعني تغيير الطبقة [dao]. يجب وضع هذه الحجة الثانية في سياقها الصحيح: لا تقوم الشركات بتغيير SGBD كثيرًا. علاوة على ذلك، سنرى لاحقًا أنه منذ الإصدار 2.0 من .NET، يوجد موصل عام يوفر المرونة دون التضحية بالأداء.

    9.2. طريقتان لاستخدام مصدر البيانات

    تسمح منصة .NET باستغلال مصدر البيانات بطريقتين مختلفتين:

    1. الوضع المتصل
    2. الوضع غير المتصل

    في الوضع المتصل، تقوم التطبيق

    1. اتصالاً بمصدر البيانات
    2. يعمل مع مصدر البيانات في وضع القراءة/الكتابة
    3. يغلق الاتصال

    في وضع عدم الاتصال، يقوم التطبيق

    1. يفتح اتصالاً بمصدر البيانات
    2. يحصل على نسخة في الذاكرة من كل أو جزء من بيانات المصدر
    3. يغلق الاتصال
    4. يعمل مع نسخة الذاكرة من البيانات للقراءة/الكتابة
    5. عند انتهاء العمل، يفتح اتصالاً، ويرسل البيانات المعدلة إلى مصدر البيانات ليتم تضمينها، ويغلق الاتصال

    9.3.2. الأوامر الأساسية الأربعة للغة SQL

    SQL (Structured Language Query) هي لغة، معيارية جزئيًا، للاستعلام عن قواعد البيانات وتحديثها. تتوافق جميع لغات SGBD مع الجزء المعياري من لغة SQL، لكنها تضيف إلى اللغة امتدادات خاصة تستفيد من بعض خصائص لغة SGBD. لقد صادفنا بالفعل مثالين على ذلك: غالبًا ما يعتمد الإنشاء التلقائي للمفاتيح الأساسية والأنواع المسموح بها لأعمدة الجدول على لغة SGBD.

    الأوامر الأساسية الأربعة للغة SQL التي نقدمها هي أوامر موحدة ومقبولة من قبل جميع SGBD:

    select col1, col2,... 
from table1, table2,...
where condition
order by expression
...
    الاستعلام الذي يسمح بالحصول على البيانات الموجودة في قاعدة البيانات. الكلمات الرئيسية في السطر الأول هي فقط إلزامية، أما البقية فهي اختيارية. هناك كلمات رئيسية أخرى غير مذكورة هنا.
    1. يتم إجراء ربط مع جميع الجداول الموجودة خلف الكلمة الرئيسية from
    2. يتم الاحتفاظ فقط بالأعمدة الموجودة خلف الكلمة الرئيسية select
    3. يتم الاحتفاظ فقط بالصفوف التي تستوفي شرط الكلمة الرئيسية where
    4. تشكل الأسطر الناتجة المرتبة وفقًا للتعبير الوارد في الكلمة الرئيسية order by نتيجة الاستعلام. هذه النتيجة عبارة عن جدول. 
    insert into table(col1,col2, ...)
values (val1,val2, ...)
    يُدرج سطراً في الجدول. (col1, col2, ...) يحدد أعمدة السطر المراد تهيئتها بالقيم (val1, val2, ...).
    update table
set col1=val1, col2=val2
where condition
    يُحدّث صفوف الجدول التي تستوفي الشرط (جميع الصفوف في حالة عدم وجود where). بالنسبة لهذه الصفوف، يتلقى العمود coli القيمة vali
    delete from table
where condition
    يحذف جميع صفوف الجدول التي تتحقق من الشرط

    سنقوم بكتابة تطبيق وحدة تحكم يسمح بإصدار أوامر SQL على قاعدة البيانات [dbarticles] التي أنشأناها سابقًا. فيما يلي مثال على التنفيذ. يُطلب من القارئ فهم الأوامر SQL الصادرة ونتائجها.

    9.3.3. واجهات ADO.NET الأساسية للوضع المتصل

    لنعد إلى مخطط تطبيق يستخدم قاعدة بيانات عبر موصل ADO.NET:

    في الوضع المتصل، يقوم التطبيق بما يلي:

    1. يفتح اتصالاً بمصدر البيانات
    2. تعمل مع مصدر البيانات في وضع القراءة/الكتابة
    3. يغلق الاتصال

    هناك ثلاث واجهات ADO.NET معنية بشكل أساسي بهذه العمليات:

    • IDbCommand التي تغلف خصائص وأساليب الأمر SQL الذي تم تنفيذه.
    • IDataReader التي تغلف خصائص وأساليب نتيجة أمر SQL Select.

    9.3.7. تنفيذ استعلام SELECT

    يتطلب تنفيذ الأوامر SQL الخطوات التالية:

    1. الاتصال بقاعدة البيانات
    2. إرسال الأوامر SQL إلى قاعدة البيانات
    3. معالجة نتائج الأمر SQL
    4. إغلاق الاتصال

        static void ExecuteUpdate(string connectionString, string requête) {
            // إدارة الاستثناءات المحتملة
            try {
                using (SqlCeConnection connexion = new SqlCeConnection(connectionString)) {
                    // فتح اتصال
                    connexion.Open();
                    // تنفيذ sqlCommand مع طلب التحديث
                    SqlCeCommand sqlCommand = new SqlCeCommand(requête, connexion);
                    int nbLignes = sqlCommand.ExecuteNonQuery();
                    // عرض النتيجة
                    Console.WriteLine("Il y a eu {0} ligne(s) modifiée(s)", nbLignes);

            } catch (Exception ex) {
                // رسالة خطأ
                Console.WriteLine("Erreur d'accès à la base de données (" + ex.Message + ")");

}

    9.4.6. ما هو الموصل الذي يجب اختياره؟

    لنعد إلى بنية تطبيق يستخدم قواعد البيانات:

    لقد رأينا أنواعًا مختلفة من الموصلات ADO.NET:

    • الموصلات الخاصة هي الأكثر أداءً ولكنها تجعل الطبقة [dao] تعتمد على فئات خاصة. تغيير SGBD يعني تغيير الطبقة [dao].
    • تسمح الموصلات ODBC أو OLE DB بالعمل مع قواعد بيانات متعددة دون تغيير الطبقة [dao]. وهي أقل أداءً من الموصلات الخاصة.
    • يعتمد الموصل العام على الموصلات الخاصة مع تقديم واجهة قياسية لطبقة [dao].

    لذلك يبدو أن الموصل العام هو الموصل المثالي. لكن في الواقع، لا يستطيع الموصل العام إخفاء جميع خصائص SGBD خلف واجهة قياسية. سنرى في الفقرة التالية مفهوم الاستعلام المعلم. مع خادم SQL، يكون الاستعلام المعلم بالشكل التالي:

    insert into articles(nom,prix,stockactuel,stockminimum) values(@nom,@prix,@sa,@sm)

    مع MySQL5، يُكتب نفس الاستعلام على النحو التالي:

    insert into articles(nom,prix,stockactuel,stockminimum) values(?,?,?,?)

    لذلك هناك اختلاف في الصيغة. خاصية واجهة IDbCommand الموصوفة في الفقرة 9.3.3، والمتعلقة بالمعلمات هي كما يلي:

    Parameters
    قائمة معلمات أمر SQL الذي تم تعيين معلماته. يحتوي الأمر update articles set prix=prix*1.1 where id=@id على المعلمة @id.

    الخاصية Parameters هي من النوع IDataParameterCollection، وهي واجهة. وهي تمثل مجموعة معلمات الأمر SQL CommandText. تحتوي الخاصية Parameters على طريقة Add لإضافة معلمات من النوع IDataParameter، وهي واجهة أيضًا. وتحتوي هذه الواجهة على الخصائص التالية:

    • ParameterName: اسم المعلمة
    • DbType: نوع المعلمة SQL
    • Value: القيمة المخصصة للمعلمة
    • ...

    يناسب النوع IDataParameter المعلمات من النوع SQL 

    insert into articles(nom,prix,stockactuel,stockminimum) values(@nom,@prix,@sa,@sm)

    لأنه يحتوي على معلمات مسماة. يمكن استخدام الخاصية ParameterName.

    النوع IDataParameter غير مناسب للأمر SQL 

    insert into articles(nom,prix,stockactuel,stockminimum) values(?,?,?,?)

    لأن المعلمات غير مسماة. وفي هذه الحالة، يتم أخذ ترتيب إضافة المعلمات في المجموعة [IDbCommand.Parameters] في الاعتبار. في هذا المثال، يجب إدراج المعلمات الأربعة بالترتيب nom، prix، stockactuel، stockminimum. في الاستعلام الذي يحتوي على معلمات مسماة، لا يهم ترتيب إضافة المعلمات. في النهاية، لا يمكن للمطور تجاهل SGBD تمامًا الذي يستخدمه عند تهيئة معلمات استعلام معلم. هذه إحدى القيود الحالية للموصل العام.

    هناك frameworks تتجاوز هذه القيود وتوفر أيضًا ميزات جديدة لطبقة [dao]:

    الإطار هو مجموعة من مكتبات الفئات التي تهدف إلى تسهيل طريقة معينة لتصميم التطبيق. هناك العديد منها التي تسمح بكتابة طبقات [dao] عالية الأداء وغير حساسة لتغيير SGBD:

    • Spring.Net [http://www.springframework.net/] الذي تم عرضه سابقًا في هذا المستند يقدم ما يعادل الموصل العام الذي تمت دراسته، دون قيوده، بالإضافة إلى ميزات متنوعة تبسط الوصول إلى البيانات. توجد نسخة Java.
    • iBatis.Net [http://ibatis.apache.org] أقدم وأكثر ثراءً من Spring.Net. توجد نسخة Java.
    • NHibernate [http://www.hibernate.org/] هو نسخة معدلة من إصدار Java Hibernate الشهير في عالم Java. يسمح NHibernate للطبقة [dao] بالتبادل مع SGBD دون إصدار أوامر SQL. تعمل الطبقة [dao] مع كائنات Hibernate. تسمح لغة الاستعلامات HBL (لغة استعلامات Hibernate) بالاستعلام عن الكائنات التي تديرها Hibernate. وهذه الكائنات هي التي تصدر أوامر SQL. يستطيع Hibernate التكيف مع SQL المالكين لـ SGBD.
    • LINQ (لغة استعلام INtegrated)، مدمجة في الإصدار 3.5 .NET ومتوفرة في C# 2008. LINQ يسير على خطى NHibernate، ولكن في الوقت الحالي (مايو 2008) لا يتم دعم سوى خادم SGBD SQL. ومن المتوقع أن يتغير هذا مع مرور الوقت. يتجاوز LINQ نطاق NHibernate: حيث تتيح لغة الاستعلامات الخاصة به الاستعلام بشكل قياسي عن ثلاثة أنواع مختلفة من مصادر البيانات:
      • مجموعات الكائنات (LINQ to Objects)
      • ملف Xml (LINQ to Xml)
      • قاعدة بيانات (LINQ to SQL)

    لن يتم تناول هذه الأطر في هذا المستند. ومع ذلك، يُنصح بشدة باستخدامها في التطبيقات الاحترافية.

    9.6.1. معلومات عامة

    المعاملة هي سلسلة من الأوامر SQL التي يتم تنفيذها بشكل "أتمي":

    • إما أن تنجح جميع العمليات
    • إما أن تفشل إحداها، وفي هذه الحالة يتم إلغاء جميع العمليات التي سبقتها

    في النهاية، إما أن يتم تنفيذ جميع عمليات المعاملة بنجاح، أو لا يتم تنفيذ أي منها. عندما يكون المستخدم هو من يتحكم في المعاملة، فإنه يصادق عليها بأمر COMMIT أو يلغيها بأمر ROLLBACK.

    في الأمثلة السابقة، لم نستخدم أي معاملة. ومع ذلك، كانت هناك معاملات، لأن الأمر SQL في SGBD يتم تنفيذه دائمًا ضمن معاملة. إذا لم يبدأ العميل .NET بنفسه معاملة صريحة، فإن SGBD يستخدم معاملة ضمنية. وهناك حالتان شائعتان:

    1. يخضع كل أمر SQL فردي لمعاملة، تبدأ بواسطة SGBD قبل الأمر وتُغلق بعده. يُقال إننا في وضع autocommit. لذلك، تسير الأمور كما لو أن العميل .NET يقوم بمعاملات لكل أمر SQL.
    2. لا يعمل SGBD في وضع autocommit ويبدأ معاملة ضمنية عند الأمر الأول SQL الذي يصدره العميل .NET خارج نطاق معاملة، ويترك للعميل مهمة إغلاقها. تصبح جميع الأوامر SQL التي يصدرها العميل .NET جزءًا من المعاملة الضمنية. ويمكن أن تنتهي هذه المعاملة بناءً على أحداث مختلفة: يقوم العميل بإغلاق الاتصال، أو يبدأ معاملة جديدة، ... ولكننا نكون عندئذ في وضع يعتمد على SGBD. وهذا وضع يجب تجنبه.

    يتم تحديد الوضع الافتراضي عمومًا من خلال تكوين SGBD. بعض SGBD تكون في وضع autocommit بشكل افتراضي، والبعض الآخر لا. SQLServer Compact تكون في وضع autocommit بشكل افتراضي.

    يتم تنفيذ أوامر SQL الخاصة بالمستخدمين المختلفين في نفس الوقت في معاملات تعمل بالتوازي. قد تؤثر العمليات التي تقوم بها إحدى المعاملات على تلك التي تقوم بها معاملة أخرى. هناك أربعة مستويات من العزل بين معاملات المستخدمين المختلفين:

    • قراءة غير ملتزم بها
    • قراءة ملتزم بها
    • قراءة قابلة للتكرار
    • قراءة قابلة للتسلسل

    قراءة غير ملتزم بها

    يُطلق على وضع العزل هذا أيضًا اسم "قراءة غير نظيفة". فيما يلي مثال على ما قد يحدث في هذا الوضع:

    1. يبدأ المستخدم U1 معاملة على الجدول T
    2. يبدأ المستخدم U2 معاملة على نفس الجدول T
    3. يقوم المستخدم U1 بتعديل صفوف الجدول T ولكنه لم يقم بتأكيدها بعد
    4. المستخدم U2 "يرى" هذه التعديلات ويتخذ قرارات بناءً على ما يراه
    5. يقوم المستخدم بإلغاء معاملته بواسطة ROLLBACK

    نلاحظ أنه في الخطوة 4، اتخذ المستخدم U2 قرارًا بناءً على بيانات ستتضح لاحقًا أنها خاطئة.

    القراءة الملتزم بها

    يمنع وضع العزل هذا المعضلة السابقة. في هذا الوضع، لن "يرى" المستخدم U2 في الخطوة 4 التعديلات التي أجراها المستخدم U1 على الجدول T. ولن يراها إلا بعد أن يقوم U1 بإجراء COMMIT لمعاملته.

    في هذا الوضع، الذي يُعرف أيضًا باسم "Unrepeatable Read"، قد نواجه مع ذلك الحالات التالية:

    1. يبدأ المستخدم U1 معاملة على الجدول T
    2. يبدأ مستخدم U2 معاملة على نفس الجدول T
    3. يقوم المستخدم U2 بإجراء SELECT للحصول على متوسط العمود C من صفوف T التي تستوفي شرطًا معينًا
    4. يقوم المستخدم U1 بتعديل (UPDATE) بعض القيم في العمود C من T والتحقق من صحتها (COMMIT)
    5. يقوم المستخدم U2 بإعادة تنفيذ نفس SELECT كما في 3. وسيكتشف أن متوسط العمود C قد تغير بسبب التعديلات التي أجراها U1.

    الآن لا يرى المستخدم U2 سوى التعديلات التي "تمت الموافقة عليها" بواسطة U1. ولكن بينما يظل في نفس المعاملة، تعطي عمليتان متطابقتان 3 و 5 نتائج مختلفة. يشير مصطلح "Unrepeatable Read" إلى هذه الحالة. إنها حالة مزعجة لمن يرغب في الحصول على صورة ثابتة للجدول T.

    القراءة القابلة للتكرار

    في وضع العزل هذا، يضمن المستخدم الحصول على نفس النتائج لقراءاته من قاعدة البيانات طالما بقي في نفس المعاملة. فهو يعمل على نسخة لا تنعكس عليها أبدًا التعديلات التي أجرتها المعاملات الأخرى، حتى لو تم تأكيدها. ولن يرى هذه التعديلات إلا عندما ينهي المعاملة بنفسه باستخدام COMMIT أو ROLLBACK.

    ومع ذلك، فإن وضع العزل هذا ليس مثاليًا بعد. بعد العملية 3 أعلاه، يتم قفل الأسطر التي استشارها المستخدم U2. أثناء العملية 4، لن يتمكن المستخدم U1 من تعديل (UPDATE) قيم العمود C في هذه الأسطر. ومع ذلك، يمكنه إضافة أسطر (INSERT). إذا كانت بعض الأسطر المضافة تستوفي الشرط الذي تم اختباره في الخطوة 3، فستعطي العملية 5 متوسطًا مختلفًا عن المتوسط الذي تم الحصول عليه في الخطوة 3 بسبب الأسطر المضافة. تسمى هذه الأسطر أحيانًا بالأسطر الوهمية.

    لحل هذه المشكلة الجديدة، يجب الانتقال إلى العزل "Serializable".

    Serializable

    في وضع العزل هذا، تكون المعاملات معزولة تمامًا عن بعضها البعض. ويضمن أن نتيجة معاملتين يتم إجراؤهما في وقت واحد ستعطي نفس النتيجة كما لو تم إجراؤهما واحدة تلو الأخرى. للوصول إلى هذه النتيجة، في العملية 4 حيث يريد المستخدم U1 إضافة أسطر من شأنها تغيير نتيجة SELECT للمستخدم U1، سيتم منعه من ذلك. ستظهر له رسالة خطأ تفيد بأن الإدراج غير ممكن. وسيصبح ذلك ممكنًا عندما يقوم المستخدم U2 بتأكيد معاملته.

    مستويات عزل المعاملات الأربعة SQL غير متوفرة في جميع SGBD. عادةً ما يكون مستوى العزل الافتراضي هو مستوى Committed Read. يمكن تحديد مستوى العزل المطلوب لمعاملة ما بشكل صريح عند إنشاء معاملة صريحة بواسطة عميل .NET.

    يُنفذ الاتصال واجهة IDbConnection الموضحة في الفقرة 9.3.3. تحتوي هذه الواجهة على الطريقة التالية:

    BeginTransaction
    M

    هذه الطريقة لها توقيعان:

    1. IDbTransaction BeginTransaction(): تبدأ معاملة وتُرجع الكائن IDbTransaction الذي يسمح بالتحكم فيها
    2. IDbTransaction BeginTransaction(IsolationLevel level): تحدد أيضًا مستوى السرية المطلوب للمعاملة. تأخذ level قيمها من التعداد التالي: 
    ReadUncommitted
    يمكن للمعاملة قراءة البيانات المكتوبة بواسطة معاملة أخرى لم تقم هذه الأخيرة بالتحقق من صحتها بعد - يجب تجنب ذلك
    ReadCommitted
    لا يمكن للمعاملة قراءة البيانات التي كتبتها معاملة أخرى ولم تقم هذه الأخيرة بالتحقق منها بعد. ومع ذلك، قد تتغير البيانات التي تمت قراءتها مرتين متتاليتين في المعاملة (قراءات غير قابلة للتكرار) لأن معاملة أخرى قد قامت بتعديلها في غضون ذلك (السطور التي تمت قراءتها غير مقفلة - فقط السطور التي تم تحديثها هي المقفلة). علاوة على ذلك، قد تكون معاملة أخرى قد أضافت أسطرًا (أسطر وهمية) سيتم تضمينها في القراءة الثانية.
    RepeatableRead
    يتم قفل الصفوف التي تقرأها المعاملة تمامًا مثل الصفوف التي يتم تحديثها. وهذا يمنع أي معاملة أخرى من تعديلها. لكنه لا يمنع إضافة صفوف جديدة.
    Serializable
    يتم قفل الجداول التي تستخدمها المعاملة، مما يمنع إضافة أسطر جديدة بواسطة معاملة أخرى. كل شيء يسير كما لو كانت المعاملة هي الوحيدة. يقلل من الأداء لأن المعاملات لم تعد تعمل بالتوازي.
    Snapshot
    تعمل المعاملة على نسخة من البيانات تم إنشاؤها في الوقت T. تُستخدم عندما تكون المعاملة للقراءة فقط. تعطي نفس نتيجة serializable مع تجنب تكلفتها.

        public DataBaseImpot(string factory, string connectionString, string requête) {
